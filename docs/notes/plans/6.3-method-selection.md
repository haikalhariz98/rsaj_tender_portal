# 6.3 Method selection, value bands, contract type: plan

Spec: §6.3 (FR-MTD-001–014), §4.2, §4.4, §4.5, §7.3.2, §8.1, §8.12 R2, §12 (D3, D12, D13, B3, B8), §13.3. Also FR-REQ-013 and FR-REQ-014, carried here from 6.1.
Builds on 6.1 (`Requisition`, `ApprovalInstance`/`ApprovalStep`, `issueReference`, `AuthorityRule.followsBoundarySwitch`).
Decision record: `docs/notes/architecture/0006-exercise-classification-and-band-families.md` (proposed).

## 0. Findings in today's code

- **One axis only.** `AuthorityMatrix` holds `quotationFloor`, `tenderFloor`, `requisitionBoundary` and `boundaryValue`, and `regimeFor` gives below/quotation/tender.
  - There is no terms band.
  - `requisitionBoundary` is loaded (`load.ts:95`) and displayed (`approval-matrix/page.tsx:300`), but no decision reads it. 6.3 must not read it either, because the requisition family is the `domain=requisition` rules (6.1).
- **`boundaryValue` and `tenderFloor` are two columns that should say the same thing.** If they differ, the D3 switch governs no regime edge. Nothing checks this.
- **`SourcingMethod` has regime flags but no behaviours.** It has no default method per regime, no justification, proposal, name approval, restriction or emergency record. `ContractType` is a label only.
- **Domain keys disagree.** The authority fixture uses domain `appointment`; `demo_mx1` uses `purchase`. 6.3 standardises on `appointment`.
- **No exercise exists.** `/sourcing` is `NotBuilt`. `MatterKind.EXERCISE` exists (6.10).
- **The spec contradicts itself on basis.** FR-MTD-013 makes basis an independent axis that must be chosen, yet FR-MTD-014 says the mapping "populates the SK001 basis" (OD-4).
- **The taxonomies do not map 1:1.** Three canonical types cannot determine seven performance-report forms (Works vs Design and Build), so mapping needs discriminators and an AMBIGUOUS state (OD-5).
- **D13 asymmetry.** A direct appointment escalates to Chairman/Board; a tender never does. This is configuration, and 6.3 must not "fix" it (a test asserts it).

Rules for writes:
- **State lives on the row.** Every write goes through `auditedUpdate` (before and after, same transaction). Reasons are required for cancel, method override, type override and value change.
- **Rules for creating an exercise.** Creation is refused unless the requisition is APPROVED and `sourcingPermitted` is true. The first move to DOCUMENTS_IN_PREPARATION sets the requisition to SOURCING in the same transaction.
- **Cancellation.** CANCELLED is marked as an assumption on screen (§7.3.2 gives no SOP path for it).
- **Contract type on the requisition.** 6.1's `Requisition.contractTypeCode` is the requester's indication. It pre-fills the exercise; the exercise's value is the controlled one.
