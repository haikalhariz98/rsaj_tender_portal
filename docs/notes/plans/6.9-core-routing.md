# 6.9 R3: core routing (chain generation), design note

Spec: FR-APR-004, §6.9.2 ("Core routing rule, §2.2.1, 4 × 4"), Appendix B.1–B.4, §6.9.3 examples 1, 2, 5, CO-9, C5.
Ruling: decisions log 2026-10-01 · 6.9 · FR-APR-004 NOT MET → must-fix (R3). Design only; build order in §10.

## 0. Findings in today's code

- No core routing: a rule's chain is whatever was typed into `proposerCode` + `recommenders`, so a rule entered without the Head of Department's P silently drops it (FR-APR-004: "cannot be shortened by a user").
- `resolveApproval` builds proposer P → recommenders → self-approval downgrade (`approver R`, *appended*) → approver; the only dedupe collapses *adjacent* identical steps.
- Chains are also built from rule fields outside the resolver: `approval-matrix/page.tsx:160` (preview), `lib/award/signatory.ts:42`, `lib/people/load.ts:59` ("routed" offices). None would see generated steps.
- `issueDraft` validates outside its transaction with no row lock; `startRevision`/`discardDraft` destructure `{ rules, termsBands, ...policy }`, so a new relation must be included and destructured out in both. Callers block only on `level === "err"`.

## 1. Decisions

| # | Decision | Why |
|---|---|---|
| D-1 | The core table is owned by the issue (`authorityMatrixId`): copied on revision, frozen when issued, like `TermsBand`. | FR-APR-020: revising §2.2.1 is revising the DAL. |
| D-2 | Rows keyed by the approving office's role code, not `authorityLevel`. | Steps are concrete offices; `authorityLevel` is a free label several roles share. |
| D-3 | Any office may have a row (BOD, Chairman, a committee), with provenance — not only B.2's four. | §2.2.1 is silent above CEO; example 5 needs a BOD row (OQ-2). |
| D-4 | Core beneath-acts are P, JP, R, JR only. | B.2 prints nothing mandatory beneath an approver; mandatory acts come only from rules, so `ruleIsDelegable` stays correct. |
| D-5 | `AuthorityRule.generateCoreChain Boolean?`: null not set, true generate, false decided "as entered". | Three-state honesty; false is a decision. |
| D-6 | Generate beneath `rule.approverCode` before self-approval/absence escalation; never regenerate for the escalated office. | FR-APR-008 moves the approval only; regenerating duplicates offices. |

## 2. Schema (one additive migration `6_9_core_routing`; hand-checked SQL, no `;` inside comments, `migrate diff` empty)

```prisma
/// One approving office's row of the core routing rule (§2.2.1) in one issue. Ships empty.
/// A row with no steps means "approves alone", which is not the same as no row.
model CoreRoutingLevel {
  id                String            @id @default(cuid())
  organisationId    String
  organisation      Organisation      @relation(fields: [organisationId], references: [id], onDelete: Cascade)
  authorityMatrixId String
  authorityMatrix   AuthorityMatrix   @relation(fields: [authorityMatrixId], references: [id], onDelete: Cascade)
  approverCode      String
  clause            String            @default("")
  provenance        Provenance        @default(ASSUMED)
  note              String            @default("")
  sortOrder         Int               @default(0)
  steps             CoreRoutingStep[]
  @@unique([authorityMatrixId, approverCode])
  @@index([organisationId])
}

/// An office beneath the approver, in order. act is P, JP, R or JR (enforced in src/lib).
model CoreRoutingStep {
  id                 String           @id @default(cuid())
  organisationId     String
  organisation       Organisation     @relation(fields: [organisationId], references: [id], onDelete: Cascade)
  coreRoutingLevelId String
  level              CoreRoutingLevel @relation(fields: [coreRoutingLevelId], references: [id], onDelete: Cascade)
  roleCode           String
  act                AuthorityAct
  sequence           Int
  provenance         Provenance       @default(ASSUMED)
  note               String           @default("")
  @@unique([coreRoutingLevelId, sequence])
  @@unique([coreRoutingLevelId, roleCode])
}
```

Also, all nullable with no backfill (earlier routes read "Not recorded", never today's configuration):
- `AuthorityRule.generateCoreChain Boolean?` and `AuthorityRule.coreChainReason String?` (OQ-4); `AuthorityMatrix.coreRouting CoreRoutingLevel[]`; two back-relations on `Organisation`.
- `ApprovalInstance.coreChainFlag Boolean?` (the flag as it stood) and `coreRoutingSnapshot Json?` (level used: approver, clause, provenance, steps).
- `ApprovalStep.chainOrigin ChainStepOrigin?` with `enum ChainStepOrigin { CORE CORE_STRENGTHENED RULE }`.

## 3. Strength order across the eight acts (`ACT_RANK` in `src/lib/authority/core-routing.ts`)

| Rank | Acts | Justification |
|---|---|---|
| 1 | P, JP | B.2 climbs Propose → Recommend → Approve as an office nears the approver; its CEO row prints "Propose / Jointly Propose" as one cell. |
| 2 | R, JR | B.4 prints "JR/R Head of Div" as alternatives for one cell: joint and sole share a rank. |
| 3 | MR, MJR | B.1, §1.6: the same act made non-delegable, so stricter. |
| — | A, MA | Never valid beneath an approver (`APPROVE_BENEATH`). The approver's act stays `approverAct(rule)`. |

A rule's act on a generated office is accepted iff its rank is ≥ the core act's; lower is `WEAKENS`. All six beneath-acts are comparable; joint/sole are equal because the joint partner office is not modelled (FR-APR-003 log; OQ-3). Examples need: 1 HODIV P→R, FD R→MR; 2 HODIV P→JP; 5 HODIV R→JR.

## 4. Pure functions (`src/lib/authority/core-routing.ts`, no I/O)

```ts
export type CoreStep = { roleCode: string; act: "P" | "JP" | "R" | "JR"; provenance: Provenance };
export type CoreLevel = { approverCode: string; clause: string; provenance: Provenance; steps: CoreStep[] };
export type ChainOrigin = "CORE" | "CORE_STRENGTHENED" | "RULE";
export const ACT_RANK: Record<AuthorityAct, number>;
export function atLeastAsStrong(ruleAct: AuthorityAct, coreAct: AuthorityAct): boolean;
export function coreLevelFaults(level: CoreLevel, roles: Record<string, Role>): CoreLevelFault[];
export function generateChain(rule: Rule, core: readonly CoreLevel[] | undefined, roles: Record<string, Role>):
  | { ok: true; steps: (ApprovalStep & { origin: ChainOrigin })[]; level: CoreLevel }
  | { ok: false; fault: CoreChainFault; roleCode?: string };
export function coreChainFaultsAcross(rules: readonly Rule[], core: readonly CoreLevel[]): { rule: Rule; fault: CoreChainFault; roleCode?: string }[]; // flagged only
export function copyCoreRouting(levels: readonly CoreLevelRow[], to: { authorityMatrixId: string; organisationId: string }): Prisma.CoreRoutingLevelCreateInput[];
```

`Matrix` gains optional `coreRouting?: CoreLevel[]` (absent or `[]` = not set), so `fixture.ts` and other literals still compile.

**Merge (steps before the approver), in order:** (1) a rule `proposerCode` whose office is *not* in the core row — P, origin RULE; (2) the core row's steps in core order, each overlaid by the rule's act where the rule names that office as proposer (P) or recommender — origin CORE if identical, CORE_STRENGTHENED otherwise; (3) the rule's remaining recommenders in the order entered, origin RULE (committees such as QC MR land here); (4) the approver, as today. Every emitted step, overlaid or not, takes `nonDelegable = MANDATORY_ACTS.has(finalAct)` and `committeeCode` when the role is a committee, exactly as the resolver does for rule steps (example 1 asserts FD non-delegable). "Never drop" is structural: every core step is always emitted.

`resolveApproval` calls `generateChain` only when `generateCoreChain === true`; otherwise the chain is built as today. **Self-approval (D-6):** the downgraded `approver R` merges into an existing step for that office (higher rank kept) and is appended only if the office is absent.

| Fault | Checked on | Meaning |
|---|---|---|
| `CORE_ROW_MISSING` | rule, issue | Flagged, but the issue has no core row for the rule's approver. |
| `WEAKENS` | rule, issue | The rule gives a generated office a lower-ranked act. |
| `ORDER_DIFFERS` | rule, issue | The rule names core offices in another order than the core row. |
| `APPROVER_BENEATH` | rule, level | The approving office also appears beneath itself. |
| `APPROVE_BENEATH` | rule, level | A or MA on a step beneath the approver. |
| `DUPLICATE_OFFICE` | rule, level | An office twice in one chain or row. |
| `MANDATORY_IN_CORE` | level | MR, MJR or MA in a core row (D-4). |
| `UNKNOWN_OFFICE` | level | Role code not in `AuthorityRole`. |

## 5. Resolution warnings (en and ms; office and rule names, never codes)

Never emitted on the NO_RULE path (example 14 asserts `["NO_RULE"]`).
- `CORE_NOT_CHECKED`, `warn`, flag null — chain as entered: "Chain as entered, not checked against core routing: nobody has decided whether “{rule label}” takes its chain from the core routing. Decide it on the rule in the approval matrix." / "Rantaian seperti yang dimasukkan, tidak disemak terhadap laluan teras: belum diputuskan sama ada “{rule label}” mengambil rantaiannya daripada laluan teras. Putuskan pada peraturan dalam matriks kelulusan."
- `CORE_NOT_CHECKED`, `warn`, flag true but no core row for the approver (empty table included) — chain as entered: "Chain as entered, not checked against core routing: this issue records no core routing for {office name}. Record it on the issue in the approval matrix." / "Rantaian seperti yang dimasukkan, tidak disemak terhadap laluan teras: isu ini tidak merekodkan laluan teras bagi {office name}. Rekodkan pada isu dalam matriks kelulusan." Draft/preview only in practice: issuing refuses `CORE_ROW_MISSING`.
- `CORE_CHAIN_FAULT`, `err`, flag true and `WEAKENS`/`ORDER_DIFFERS` (outside the ruling's text; drafts only): "“{rule label}” must take its chain from the core routing, but it gives {office name} a lesser act or a different place than the core routing does. Correct the rule or the core routing before relying on this route." / "“{rule label}” mesti mengambil rantaiannya daripada laluan teras, tetapi ia memberi {office name} tindakan yang lebih rendah atau kedudukan yang berbeza daripada laluan teras. Betulkan peraturan atau laluan teras sebelum bergantung pada laluan ini."
- `CORE_AS_ENTERED`, `info`, flag false: "Chain as entered on the rule: recorded as not taken from the core routing." / "Rantaian seperti yang dimasukkan pada peraturan: direkodkan sebagai tidak diambil daripada laluan teras."

## 6. Writes (actions.ts) — each one transaction, matrix row locked (`SELECT … FOR UPDATE`), audit before/after in it

- `saveCoreLevel`, `removeCoreLevel`, `saveCoreStep`, `removeCoreStep`: refuse on an issued issue (FROZEN); re-run `coreLevelFaults` on locked data; removal asks for a reason.
- `saveRule` reads the flag via the existing `tri` pattern (`""`/`"yes"`/`"no"`); when true it refuses `WEAKENS`, `ORDER_DIFFERS`, `APPROVER_BENEATH`, `DUPLICATE_OFFICE` against the current core table; `CORE_ROW_MISSING` is shown, not refused, so rules and rows may be entered in either order. `saveRecommender` runs the same check.
- `issueDraft` moves validation inside the transaction: lock the draft, re-read rules and core table, run `coreChainFaultsAcross` + `coreLevelFaults` (and the existing boundary checks); refuse per rule: "“{label}” cannot be issued: {office name} would be missing, act less than the core routing requires, or sit out of order. Correct the rule or the core routing."
- `startRevision` includes `coreRouting: { include: { steps: true } }`, destructures it out, creates rows via `copyCoreRouting` (new ids, same organisation, provenance, clause, order), and adds `coreRouting: n` to the audit diff. The flag rides the existing rule spread. `discardDraft` deletes steps then levels, auditing each row.
- Route builders (requisition, method, award) store `coreChainFlag`, `coreRoutingSnapshot` and each step's `chainOrigin`.
- `page.tsx` preview and `award/signatory.ts` read the resolver's chain; `people/load.ts` adds the in-force issue's core-step offices to "routed".

## 11. Open questions for the product owner

- **OQ-1 §3.1.4.1 v §2.2.1.** B.2 has the Head of Division *propose* beneath the CEO; B.3 has them *recommend*. Rec.: R ranks above P (§3), so the DAL row stands as a strengthening; ask RSAJ to confirm.
- **OQ-2 Above the CEO.** §2.2.1 is silent on BOD, Chairman, TBC. Rec.: rows for any office, with provenance; RSAJ records them (ASSUMED until stated) or leaves the flag null. Example 5 relies on an ASSUMED BOD row, test fixture only.
- **OQ-3 Joint v sole.** Rec.: equal rank (either may replace the other) until the joint partner office is modelled; the alternative (joint above sole) would refuse R over a core JR.
- **OQ-4 Does flag false need a reason?** Rec.: yes, required and audited — it is a decision not to check.
- **OQ-5 Key by office or authority level?** Rec.: office (D-2); revisit if a customer's levels hold several offices.
- **OQ-6 Regenerate after escalation?** Rec.: no (D-6); FR-APR-008's acceptance moves only the approver.
- **OQ-7 Funder rule sets.** Rec.: each carries its own core table, shipped empty, never copied from the organisation's (FR-APR-013).
