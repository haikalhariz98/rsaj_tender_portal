## 0. What the code says today

- **`ExerciseStatus` stops at DOCUMENTS_IN_PREPARATION** (`src/lib/method/exercise.ts` `EXERCISE_TRANSITIONS`). A second copy of the
  union sits in `src/lib/documents/attach.ts` (`OwnerFacts`); both widen together.
- **No closing date, no window, no dates of any kind** on the exercise today. 6.4's draft adds `SourcingExercise.tenderingStartOn`,
  `closingAt` and `approvedForTenderingAt`, written when Approval for Tendering is decided. 6.4 records day and time only; the
  configured date rules are 6.5's (6.4 Q-5). 6.2 builds `leadTime()` and `amendFault` taking `closingAt: Date | null`.
- **`invitationFault`** (`src/lib/method/approval.ts:174`) is built and tested. Its only caller is the award's `submitFaults`
  (`src/lib/award/appointment.ts:136`, the CO-8 condition). Nothing invites.
- **The name route approves no names.** `requestNameApproval` (`src/app/sourcing/actions.ts:492`) writes an `ApprovalInstance` with
  domain `name_approval` and `value = estimatedValue`. No list of contractors is attached to it. FR-MTD-008 approves "the name".
  Today an approved route would let *any* list be invited. This must close before invitation is enforced (§0.1, OD-4).
- **6.3 BD-7:** `resolveNameApproval` returns `HAS_COMMITTEE_STEP` and the request is refused (`NAME_ROUTE_HAS_COMMITTEE_STEP`).
  `exerciseCitationFault` (`src/lib/award/citation.ts`) refuses anything outside domain `appointment` (`NOT_AN_APPOINTMENT_MATTER`).
  Lifting BD-7 therefore needs its own citation check for `name_approval`; reusing the award's is not enough.
- **Data already drives the path.** `SourcingMethod.requiresAdvertisement` / `invitesNamedSuppliers` say whether an exercise is
  advertised or invited, so no method code is named in this module.
- **No vendor master** (6.15). The 6.11 R9 pattern applies: a name and registration snapshot plus `vendorId` with no FK.
- **No delivery.** `NotificationRule` sends nothing (INT-09 is not built and the mail platform is Zimbra). Every "notify" in §6.5 is
  a per-recipient log the officer keeps, shaped like `AwardDistribution`.
- **No scheduler or queue.** Open / Closed for Purchase, Open for Submission and Closed are reached by the clock, not by an act.
- **Document store** (ADR 0011): `AttachmentPurpose` is an enum, and owners are meeting / exercise / award / delegation, each with
  a typed FK on `DocumentAttachment` and a lock helper in `src/lib/documents/owners.ts` (BD-DS-16). A new owner kind means a new
  FK, a new lock adapter and new `OwnerFacts`.
- **Instruments:** `DocumentTemplate` bodies with whitelisted merge fields, frozen at issue (ADR 0008, `src/lib/award/merge.ts`).
- **Numbering:** `issueReference` covers the five series the portal mints (§9.5). Fee receipts are not among them. The finance
  receipt number is consumed, never minted.
- **Dates:** `src/lib/dates.ts` has days only (`dayIn`, `todayIn`, `dayToDate`). There is no "14:30 on day D in the organisation's
  zone" helper, so one is added.
- **NotBuilt pages.** None is replaced here. `/supplier/opportunities` (purchase, briefing registration, addendum acknowledgement)
  and `/supplier` are the vendor's side: Phase 3 (6.15), which needs vendor sign-in and D6. `/suppliers` is the 6.15 register.
  `/documents` is the library, `/projects` is Phase 4 and `/reports` is 6.17. Their texts stay. 6.5's screens are tabs on
  `/sourcing/[id]` plus one configuration screen.

## 4. Actions (`src/app/sourcing/[id]/window/actions.ts`, `src/app/configuration/invitation/actions.ts`)

Every write runs in one transaction. It locks the requisition, then the exercise (`withLockedRequisitionForSourcing`), then
`ExerciseWindow`, then the child row. It re-reads policy, calendar, routes and sales inside the transaction, re-runs the pure check
on the locked data, writes, and audits before/after in the same transaction. Persons are "recorded on behalf of, not signed". The
derived phase is recomputed under the lock on every write, never trusted from the form.

1. `saveWindow`, `saveFeeLines`: editable until publication. They never touch `tenderingStartOn` / `closingAt`. The first write
   records 6.4's approved dates as the APPROVED `ClosingChange`.
2. `proposeInvitee` / `removeInvitee`: a change while a name route is PENDING or APPROVED withdraws it in the same transaction
   (`WITHDRAWN_ON_CHANGE`). `requestNameApproval` is extended to write `NameRouteInvitee` rows. `citeNameDecision` discharges a
   committee step (`nameCitationFault`).
3. `recordPublication`, `publish` (→ ADVERTISED / INVITED, `advertisementDay` and `policySnapshot` frozen).
   `issueInvitationLetters` freezes one text per invitee.
4. `recordSale`, `voidSale` (reason; refused once the party holds a 6.6 envelope). `recordSaleCheck`.
5. `scheduleEvent`, `recordAttendance`, `markHeld`.
6. `draftAddendum`, `issueAddendum` (number allocated under the window lock; recipients snapshotted), `recordDelivery`.
7. `requestClosingChange` / `requestCancellation` open an `ApprovalInstance` (exerciseId, domain `window_change`, cond EXTENSION /
