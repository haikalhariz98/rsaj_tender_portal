# 6.1 Requisition and intake, funding route, budget check — plan

Spec: §6.1 (FR-REQ-001–016), §4.2.1, §4.3, §7.1/7.3.1, §7.4, §8.1–8.2, INT-01/02, §12 (B7, D3, D5, OQ-06).
Decision records (status **proposed**): `docs/notes/architecture/0003-requisition-two-entry-paths.md`,
`0004-budget-check-reads-the-movement-ledger.md`, `0005-approval-instance-and-steps.md`.
(0001/0002 are taken by the 6.10 plan. If they collide at commit time, renumber these.)

## 0. What the code says today (findings)

- **Two budget ledgers.** `BudgetAllocation`/`BudgetCommitment` (keyed on cost centre + account code) is read by
  `checkAgainstBudget` (`src/lib/budget/availability.ts`). Its editors (`AddAllocation`/`EditAllocation` in
  `src/app/configuration/budget/editors.tsx`) are **imported by no panel**, so no screen writes it. Only `demo.ts` does.
  The Budget screen is `BudgetCode` + `BudgetMovement` throughout (`figuresFor` in `src/lib/budget/codes.ts`).
  `BudgetCode` has an `accountCode` and an `owningUnitCode`, but **no cost centre**.
- **Numbering never issues.** `afterIssuing` is pure and returns the next state, but no caller exists. No row lock or unique backstop.
- **The approval engine only resolves.** No approval instance or step is persisted anywhere. The funder override is
  a warning (`GOV_OVERRIDE`). No alternative rule set exists.
- **`AuthorityMatrix.splittingWindowDays @default(30)` is a shipped guess**, and it is already in issued (frozen) rows.
  Nothing reads it except `loadMatrix`. It is superseded below. The column stays and is not read.
- **D3 leaks into requisitions.** `inBand` flips *any* band edge equal to `boundaryValue`. A requisition rule with
  `maxValue = 300000` therefore inherits the quotation/tender boundary switch (see OD-4).
- **The spec contradicts itself.** §7.4 and INT-01 make the ERP the master of requisition, budget check and DAL chain.
  FR-REQ-001–009 ask the portal to do all three. Resolved by two entry paths into one state machine (ADR 0003).

  **The issue lifecycle is partitioned by `fundingRouteCode`.** Issuing a funder rule set must not end the organisation's own

entering the record (the same pattern as `Vote.personId`). The audit row stays `unattributed`. Nothing fakes sign-in.

### 2.3 Intake façade (INT-01/02): `src/lib/integration/`

- `requisition-intake.ts` defines `ExternalRequisition` (the INT-01 payload: PROC, NM, unit, cost centre, account, lines,
  value, budget four-figures with as-at, approval trail as `{roleLabel, personName, act, on}[]`). It also defines
  `interface RequisitionIntake { receive(p: ExternalRequisition): Promise<IntakeResult> }`.
  The only adapter is `manualIntake`. It records `origin = EXTERNAL`, `erpRefSource = MANUAL`, and the budget check as
  `MANUAL_ERP_ENTRY`. The external trail is stored as a closed `ApprovalInstance` with `ruleKey = null` and one
  DONE step per trail entry. The engine never re-routes it.
- `budget-check.ts` defines `interface BudgetCheckProvider { check(q): Promise<BudgetSnapshot> }`. Its adapters are `portalLedger` (§3)
  and `manualEntry` (the officer types the four figures from the finance screen, and the screen says "entered by hand").
  Nothing contacts an outside system.

## 3. Budget ledger and atomic numbering

**Which ledger** (ADR 0004):
- **A (recommended).** The requisition names a `BudgetCode`, and the check reads `BudgetMovement` through `figuresFor`.
  This is the ledger every screen writes. The spec's own F1 trigger is "a Budget Code (Kod Bajet)". Cost centre and account
  are validated against the code: the account must equal `BudgetCode.accountCode`. The cost centre's unit must equal the code's
  `owningUnitCode`, or the requisition warns `COST_CENTRE_OUTSIDE_OWNER` without blocking.
- **B.** Add `costCentreCode` to `BudgetCode`, so the spec's (cost centre, account) key resolves directly. Possible later, additively, if a
  customer's codes do not map one-to-one to an account.
- **C.** Revive `BudgetAllocation`/`BudgetCommitment`. Rejected: there is no screen for it, and two sources of "available" would
  disagree.

Under A, `checkAgainstBudget`, its tests and the old tables stay untouched. ADR 0004 marks them superseded, and removal is a later decision.

Mapping of the four figures:
- `actualBudget` = `allocated`
- `balanceAsAt` = `available` on `asAt`
- `approvedAccount` = `committed + actualSpend` (**ASSUMED**, OD-5)
- `projectedBalance` = `balanceAsAt − requestedAmount`

The identity `actualBudget − approvedAccount = balanceAsAt` is tested.

On approval, a `COMMITMENT` movement (`reference` = requisition reference) is written **in the same transaction**,
only when `BudgetSettings.commitOnApproval === true`. When it is null, the screen reads "commit on approval not set" and nothing is written.
The commitment is dated on the approval date. If `postingRefusal` (`src/lib/budget/periods.ts`) returns a closed period, **the approval
itself is refused and the period is named**, because the commitment is part of the act. An unopened period is not refused, following the existing rule.

**Atomic numbering.** New `src/lib/numbering/issue.ts` (DB-touching):
`issueReference(tx: Tx, organisationId: string, key: string, on: Date): Promise<string>`.
1. Inside the caller's interactive `db.$transaction`, run `tx.$queryRaw` `SELECT * FROM "NumberingSeries" WHERE
   "organisationId"=… AND "key"=… FOR UPDATE`.
2. Compute `serialFor`, `formatReference` and `afterIssuing` (the pure functions that already exist).
3. Run `tx.numberingSeries.update`, then return the reference. The caller inserts the requisition and its audit row in the same `tx`.

- A row lock beats `UPDATE…RETURNING`, because the period-reset logic stays in tested TypeScript instead of being restated in SQL.
- `@@unique([organisationId, reference])` is the backstop.
- A missing series refuses creation with "set up the Requisitions numbering series". It never falls back to a pattern.
- A rolled-back transaction consumes no serial.
- Concurrency proof: `scripts/check-numbering-concurrency.ts`, run with `tsx`, fires 20 parallel issues and asserts they are distinct and contiguous.
  It is a script and not a vitest file, because vitest includes `src/**/*.test.ts` and `npm test` must pass without a database.
  The pure parts keep their unit tests.
