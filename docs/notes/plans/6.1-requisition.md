## 3. Budget ledger and atomic numbering

**Ledger: A, accepted.** The requisition names a `BudgetCode`, and `portalLedger` computes the check from `BudgetMovement` via `figuresFor`.
- The account must equal `BudgetCode.accountCode`.
- A cost centre whose unit is not the code's `owningUnitCode` gives the warning `COST_CENTRE_OUTSIDE_OWNER`. It does not block.
- B (add a cost centre to `BudgetCode`) stays available later, additively.
- C (revive the allocations ledger) is rejected. `checkAgainstBudget` and the old tables are superseded, not removed.

The four figures on a portal-ledger snapshot:

| Figure | Value |
|---|---|
| `actualBudget` | allocated |
| `balanceAsAt` | available |
| `approvedAccount` | committed + spent, ASSUMED |
| `projectedBalance` | balance − requested |

The verdict is computed from `balanceAsAt` and the amount only, and never reads `approvedAccount`. The identity `actualBudget − approvedAccount = balanceAsAt` is asserted on portal-ledger snapshots only. `MANUAL_ERP_ENTRY` figures are stored as typed and never "corrected".

**Commit on approval.** Only when `BudgetSettings.commitOnApproval === true`: a `COMMITMENT` movement is written in the approval transaction, dated the organisation's today. If `postingRefusal` returns a closed period, the approval is refused and the period is named. When the setting is null, the screen shows "commit on approval not set" and nothing is written.

**Numbering.** `src/lib/numbering/issue.ts`: `issueReference(tx, organisationId, key, on): Promise<string>`.
1. `SELECT … FROM "NumberingSeries" … FOR UPDATE` inside the caller's interactive transaction.
2. Existing `serialFor`/`formatReference`/`afterIssuing`.
3. Update the series.
4. The caller inserts the requisition and its audit row in the same `tx`.

`UPDATE…RETURNING` is rejected because it would restate the reset logic in SQL. The unique `reference` is the backstop. A missing series refuses creation. The concurrency proof is `scripts/check-numbering-concurrency.ts` (tsx, 20 parallel issues, distinct and contiguous). It is not a vitest file, so `npm test` needs no database.

**Funder rule sets (lifecycle).**
- `issuedInForce(asOf, fundingRouteCode: string | null = null)`. Every existing reader keeps calling it as is, and so excludes funder issues.
- `loadOverrideMatrix(org, routeCode, asOf)` passes the code.
- In `approval-matrix/actions.ts` only, the issued-list read that feeds `issueFault`/`predecessorOf` (l.492) filters on the draft's own `fundingRouteCode`. Issuing a funder issue never ends the organisation's issue, and never trips `NOT_AFTER_LATEST` on it.
- The matrix screen labels funder issues: a `Badge` "Funder rule set · <route label>".
