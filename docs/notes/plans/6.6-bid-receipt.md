### 0.1 What "sealed" can honestly mean here (the constraint that decides the design)

FR-BID-001 and NFR-SEC-003 ask for four things:
1. No user, administrator included, can read a price, document or **identity attribute** before authorised opening.
2. A privileged database query returns ciphertext.
3. Every access attempt is logged and alerted.
4. After opening, only authorised users can read it.

What Phase 2 can truthfully deliver:

- **Bid content never enters the system before opening.** The register records the envelope, not the offer. The pre-opening record
  has no price, sum, period, document or score column. 6.7 adds the offer's columns to its opening record, written only by the
  opening act (a source-scan test, the BD-DS-2 precedent). Requirement 2 holds because there is nothing to query, not because
  anything is encrypted. The screen says exactly that.
- **Identity:** a paper envelope carries the tender, not necessarily the bidder. A register that names bidders before opening would
  reveal more than the box does. By default the register records sequence, received instant, channel, receiving officer and the
  markings as written, and the bidder is named at opening (OD-2).
- **Custody stays physical.** The box, its lock and its key remain the control. The portal records custody acts: the box locked at
  closing by a named officer, and envelopes set aside. It does not claim to enforce them.
- **What it cannot claim:**
  - that an electronic bid is sealed, because none is accepted;
  - that reading is restricted, because there is no sign-in (NFR-SEC-001);
  - alerting, because there is no delivery;
  - that the estimate is ciphertext (OD-1).
  Gaps stay honest (AGENTS.md): each one is stated on the tab.
- **NFR-SEC-003 for the electronic box** needs a key no single administrator can use. Any key the server holds alone fails that
  test: whoever holds the server's environment decrypts. Two shares held by two opening officers meets it cryptographically. But
  without sign-in nobody can say who entered each share, the server process sees the secrets as they are typed, and a lost share
  needs a recovery path. Hence OD-1.

## 4. Actions (`src/app/sourcing/[id]/bids/actions.ts`)

Lock order: requisition, exercise, `ExerciseWindow`, then the envelope or extension row (the same order as 6.5). Policy, closing and
calendar are re-read inside the transaction and the pure check re-run on locked data. Every write is audited before/after in the
same transaction. Persons are "recorded on behalf of, not signed".

1. `recordReceiptNow` stamps `receivedAt` from the server inside the transaction. `recordReceiptAfterTheFact` takes an entered
   instant and a reason. Both allocate a sequence, judge lateness against the locked `closingAt` and store the snapshot.
2. `recordWithdrawal` (with the letter attached through the generic attach action) and `recordReturnedUnopened`.
   `correctEnvelope` (clerical, reason).
3. `lockBox` (LOCKED at or after closing; refused before).
4. `tableLateMatter` uses 6.10's `tableMatter` with matter kind LATE_TENDER and `bidEnvelopeId`.
   **Cross-module edits, flagged:**
   - 6.10 `tableMatter` and 6.11's `citeDecision` call `lateAdmissionFault` for EXERCISE appointment matters.
   - 6.11 `submitFaults` / `issueFaults` gain `awardValidityFault`. New tests are added; no existing test changes.
5. `recordValidityExtension` (consent attached, then applied).
6. **Cross-module edit, flagged (6.2 will be accepted by then):** 6.2's lodge action calls `recordEstimateLodgement` in its own
   transaction, under its existing exercise lock. It never goes through `recordReceiptNow`, whose NOT_PUBLISHED fault would refuse
   a lodgement made in preparation.
