# 6.2 Scope, bill of quantities and company estimate: plan

Spec: §6.2 (FR-EST-001–010), §7.1 (Sourcing Exercise, Company Estimate), §7.3.2, §11.6 (company estimate custody), §13.4 ("the estimate as a governed record, not a literal"), NFR-AUD-004, NFR-SEC-002/003, Appendix A FR-EST rows (all Absent), Appendix D (Anggaran Syarikat). Carried in: FR-REQ-014 scope tabling (6.3 R-5, "waits for 6.2").
Builds on, as built: `SourcingExercise` (DRAFT / DOCUMENTS_IN_PREPARATION / CANCELLED; `estimatedValue` bands the exercise), `ExerciseParticipant`, `SourcingMethod` behaviour flags, `ContractBasis`, `ClassificationTaxonomy`, `CommitteeDecision.exerciseId`, `holdersFor`, `src/lib/money.ts` (sen), `src/lib/requisition/lines.ts` `lineAmount`, `src/lib/audit/record.ts`, `src/lib/award/mask.ts` (the "not access control" precedent).
Status: draft for the product owner's go (2026-10-01). No code written.

## 0. Findings in today's code

- **No estimate exists anywhere.** The only "estimate" is `SourcingExercise.estimatedValue`, which drives the bands and is printed in the page header. It is the exercise value, not the anggaran syarikat, and stays that. The company estimate **must never feed bands, regime, award checks or lists**: a regime that moved with it would leak a SULIT figure through a public fact. 6.11's "above estimate within approval warns" reads the exercise value; its label is checked to say "exercise value".
- **BQ today is a text field.** `bqReference` on the emergency coordination record (FR-REQ-013). It stays; when an exercise has a BQ the record links to it instead.
- **No closing date.** Closing datetime and submission date arrive with 6.5; opening with 6.7. The one-week rule (FR-EST-007) and the post-closing lock (FR-EST-009) are built as pure checks taking `closingAt: Date | null`; null reads "Closing not set", never "in time".
- **No sign-in.** Visibility cannot be access-controlled. Precedents: FR-MTD-007 "restriction not enforced until sign-in"; BD-9/FR-AWD-008 IC masked in audit rows, "masking is not access control". Plan the honest version (§2.4, OD-1).
- **The audit trail would leak the figure.** `writeAudit` stores before/after, and the History tab renders it. Estimate audit rows must carry "Sealed (version N)", never the value (BD-9 shape).
- **No document storage, no spreadsheet library.** Excel import cannot be built without a new dependency (OD-5). CSV import/export needs none.
- **`page.tsx` for the exercise is 1,100 lines.** New tabs go in their own files.
- **Spec conflicts to carry to RSAJ:** FR-EST-010 puts the *company* estimate on the Jadual Tawaran; FR-OPN (spec l.1712) and the opening row (l.810) say the *department* estimate. And SK002 7.7.1 makes the department estimate SULIT, while 6.1/6.3 show the requisition and exercise value openly (OD-8).

## 2. Data model (one migration, `scope_bq_estimate`, additive)

### 2.1 Policy and configuration
- `ScopePolicy` (1:1 organisation, every field nullable, shipped unset): `measurementStandardLabel` + `measurementStandardProvenance`; `bqPreparerQualificationCode`; `estimateLeadDays Int?` + provenance; `estimateLeadInclusive Boolean?` (OD-3); `estimateCustodianRoleCode` (the responsible office); `estimateAuditRoleCode` (Internal Audit office); `estimateOverrideRoleCode` (who may record a late override; null = none may); `panelSignatoryLimit Int?` (null = "no limit set"); `panelContractKindTaxonomyCode`, `panelProjectStatusTaxonomyCode` (lists held as `ClassificationTaxonomy` rows); `notes`.
- `Qualification` (org, code, nameEn/Ms, governingSource, provenance, retiredOn) and `PersonQualification` (personId, qualificationCode, validFrom, validTo?, evidenceNote).
- `BqTemplate` (org, code, nameEn/Ms, `deliverableKind?`, provenance, retiredOn) and `BqTemplateSection` (templateId, number, titleEn/Ms, sortOrder).
- `RateSchedule` (org, label, issueNo, status DRAFT|ISSUED|SUPERSEDED, effectiveFrom, issuedOn, issuedByPersonId "recorded, not signed", governingSource, provenance) and `RateScheduleItem` (scheduleId, code, descriptionEn/Ms, unit, `rate Decimal(18,2)`); `@@unique([scheduleId, code])`. Issued rows frozen (lib refuses edits).
- `SpecPanelColumn` (org, code, labelEn/Ms, orgUnitCode?, sortOrder, provenance, retiredOn).
- Additive columns: `SourcingMethod.requiresCompanyEstimate Boolean?` (null shows "not set", OD-6), `SourcingMethod.scopeCommitteeCode String?`; `ContractBasis.requiresBq Boolean?`; `MatterKind` + `SCOPE`; `CommitteeDecision.bqVersionId String?` (SetNull, indexed).

### 2.2 Bill of quantities
- `BqVersion` (exerciseId, versionNo, status DRAFT|FINALISED|SUPERSEDED, templateCode?, `scopedBy` IMPLEMENTING_DEPARTMENT|SPECIALIST_CONTRACTOR|COORDINATION_MEETING, scopeStatement, `followsStandard Boolean?`, departuresText, standardLabelSnapshot, preparerPersonId, preparerQualificationSnapshot Json?, `provisionalExcludedFromFirm Boolean?`, finalisedAt, `totalsSnapshot Json?`, revisionReason); `@@unique([exerciseId, versionNo])`. At most one DRAFT per exercise (lib + locked parent row). A revision copies the latest finalised version into a new DRAFT; finalising supersedes the previous one.
- `BqSection` (versionId, number, title, sortOrder) and `BqItem` (sectionId, itemRef, description, unit, `kind` MEASURED|PRIME_COST_SUM|PROVISIONAL_SUM, `quantity Decimal(18,3)?`, `rate Decimal(18,2)?`, `amount Decimal(18,2)?` written only from lib, `provisional Boolean`, rateScheduleId?, rateItemCode?, `rateSource` SCHEDULE|ENTERED, scheduleLabelSnapshot?, scheduleEffectiveFromSnapshot?, sortOrder). Lump sums carry amount via quantity 1 × rate.

### 2.3 Specification panel
- `SpecificationPanel` (exerciseId @unique, contractKindCode?, contractKindOther, projectStatusCode?, projectStatusOther, currentRevisionNo, currentRevisionOn?, revisedRevisionNo, revisedRevisionOn?, completionPeriodText, bqVersionId? certified against, status DRAFT|VERIFIED, verifiedAt?) and `SpecPanelVerification` (panelId, columnCode, columnLabelSnapshot, personId, verifiedOn, note). Editing a verified panel clears its verifications, audited.

### 2.4 Company estimate
- `enum SecurityClass { PUBLIC INTERNAL SULIT }` (NFR-SEC-002 vocabulary; only SULIT used now).
- `CompanyEstimate` (exerciseId @unique, preparerPersonId, `classification SecurityClass @default(SULIT)`, `state` DRAFT|LODGED|DISCLOSED|VOID, currentVersionNo, lodgedAt?, retainedPlace, disclosedAt?, voidReason).
- `CompanyEstimateVersion` (estimateId, versionNo, `value Decimal(18,2)`, preparedOn (org day), preparerPersonId, reason (required from v2), bqVersionId? it was prepared against, createdAt); `@@unique([estimateId, versionNo])`; never updated or deleted (lib + test; no route writes it twice).
- `EstimateEvent` (estimateId, kind PREPARED|AMENDED|LODGED|RETAINED|VIEW_GRANTED|VIEW_REFUSED|PREPARER_REPLACED|LATE_OVERRIDE|DISCLOSED|VOIDED, personId? named, capacity, purpose, reason, versionNo?, copyNo?, at). Append-only; each written with its `AuditEntry` in one transaction. Audit `changes` carry `value: "Sealed (version N)"`, never the figure.
- Every write locks the exercise row (`SELECT … FOR UPDATE`) and re-runs the lib check on locked data (LESSONS).
